# matview — design and code review

Overall assessment: The project has an ambitious and interesting architecture: compile ordinary SQL view definitions into database-native materialized views, with trigger-based maintenance and no Python runtime dependency. Its strongest idea is combining algebraic incremental maintenance with automatic fallbacks for queries that cannot be maintained efficiently.

The main concern is not the ambition, but the complexity of making the resulting system provably correct across different SQL dialects, database versions, transaction models, and mutation semantics.

I would prioritize correctness boundaries, SQL parsing and intermediate representation, and maintainability of the compiler before adding more query features.

This review uses the repository's current `master` branch as exposed on GitHub.

## 1. Design and architecture

What works well

The three-tier maintenance model is the right general approach:

- Tier 1 — algebraic delta: maintain aggregates and projections from insert/delete/update deltas.
- Tier 2 — group-scoped recomputation: refresh only affected groups when algebraic maintenance is impractical.
- Tier 3 — full-query refresh: preserve functionality for queries that cannot be maintained incrementally.

This is a good way to balance performance against SQL feature coverage. Reference-counted auxiliary tables for distinct aggregates are also a sensible design. The native-trigger execution model is a particularly strong selling point: Python is needed for compilation and lifecycle management, not ordinary view maintenance. [README](https://github.com/CAFxX/matview?utm_source=chatgpt.com) [Strategy implementation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)

Main architectural weakness: too much lives in one place.

The implementation is an approximately 8,200-line Python module containing SQL parsing, schema introspection, query analysis, optimization, maintenance planning, SQL generation for several dialects, lifecycle management, and CLI functionality. [Source](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)

I'd split it into:

| Component      | Responsibility                                             |
| -------------- | ---------------------------------------------------------- |
| `sql_frontend` | Parsing, normalization, SQL AST                            |
| `logical_ir`   | Engine-independent relational and aggregate representation |
| `planner`      | Strategy selection, dependency analysis, cost estimation   |
| `maintenance`  | Delta rules and auxiliary-state definitions                |
| `dialects/`    | SQLite, PostgreSQL and MySQL SQL generation                |
| `manager`      | Installation, backfill, migration, recovery                |
| `cli`          | User interface and diagnostics                             |

Most importantly, introduce a typed intermediate representation (IR) between parsing and SQL generation. Today, many transformations work directly on SQL strings. An IR would make the compiler easier to reason about, test, optimize, and extend.

## 2. Implementation: the most important problems

These are the issues I'd address before adding more functionality.



P0 — Correctness

&#x20;Backfill is not concurrency-safe



The manager deliberately installs maintenance triggers before initial population. That avoids a period when writes are completely unobserved, but creates a different race: a write can be applied by the trigger and subsequently included again in the backfill.

The sequence is explicit: create structures, install triggers, commit, populate (potentially in separate batches), then commit the catalog entry. [Registration implementation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)

For example, a row inserted after trigger installation but before its backfill chunk is read can contribute to the materialized result twice. Depending on the maintenance strategy, this can produce incorrect aggregates or uniqueness errors.

Recommendation: introduce an actual initialization protocol:

- Establish a consistent snapshot and prevent uncoordinated writes during baseline population; or
- Capture concurrent changes in a durable change log, populate from a snapshot, and replay changes after a well-defined sequence/commit watermark.

The same protocol needs to work for both full and incremental backfills.



P0 — Correctness

&#x20;SQLite `REPLACE` can bypass maintenance



The manager executes `PRAGMA recursive_triggers = ON`, but only on its own connection. SQLite trigger settings affect the connection, not every connection accessing the database. Furthermore, SQLite explicitly documents that the deletes performed by `REPLACE` fire delete triggers only when recursive triggers are enabled. [SQLite PRAGMA documentation](https://www.sqlite.org/pragma.html?utm_source=chatgpt.com) [SQLite conflict resolution documentation](https://www.sqlite.org/lang_conflict.html?utm_source=chatgpt.com)

Consequently, an ordinary application connection using `INSERT OR REPLACE` can delete an existing base-table row without invoking the materialized view's delete-maintenance trigger.

The code even records `has_on_conflict_replace` during schema parsing, but that information does not appear to be integrated into the enforcement logic.

Recommendation: either prohibit this mutation pattern, or provide an enforceable connection-initialization contract and reject unsupported configurations. Add a regression test using two independent SQLite connections, with recursive triggers disabled on the application connection.



P0 — Correctness

&#x20;SQLite bitwise aggregates are limited to 32 bits



The SQLite implementations of `BIT_AND`, `BIT_OR` and `BIT_XOR` iterate over `range(32)`. The same limitation appears in the raw-query rewriting used for fallback views. [Aggregate implementation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)

SQLite integers are signed 64-bit values, so bits above bit 31 are not represented correctly.

Recommendation: implement the full supported integer width, including negative numbers and bit 63, or explicitly restrict the supported range and reject unsupported inputs.



P1 — Performance

&#x20;Tier 3 can become catastrophically expensive



The fallback implementation refreshes the entire backing table with `DELETE` followed by `INSERT ... SELECT`. That is reasonable as a correctness fallback, but the trigger emitter invokes the supplied maintenance statements per affected row on row-trigger engines.

Even PostgreSQL's transition-table path iterates through individual transition rows. For Tier 3, where the statements themselves perform a complete refresh, a multi-row statement can therefore execute the same full refresh repeatedly. [Fallback generation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com) [PostgreSQL transition-table implementation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)

Recommendation: execute one refresh per SQL statement, not per row. PostgreSQL can do this directly with statement-level triggers. For SQLite and MySQL, consider an explicit batch-maintenance protocol or a documented refresh mechanism. Make the potentially extreme cost visible in the plan.



P1 — Reliability

&#x20;Installation and rebuilding are not atomic



Rebuilding first drops the existing view and then creates and commits the replacement structures, installs triggers, populates data, and finally records the new catalog entry. [Registration implementation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)

A failure during this sequence can leave the previous working view gone and new objects partially installed or unregistered.

`bulk_changes()` also temporarily drops maintenance triggers and recreates them before repopulating the backing tables. This requires careful coordination with other writers; it is not intrinsically safe in the presence of concurrent application connections. [Bulk implementation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)

Recommendation: use shadow backing tables and versioned maintenance objects, populate them, validate them, and switch over only after successful initialization. Where transactional DDL isn't available, use a recoverable migration state machine and explicit write coordination.

A few additional implementation issues:

- Schema signatures are incomplete. `_compute_signature()` hashes column properties, but not foreign-key cascade actions or other relevant table semantics. A change in a MySQL cascading constraint may therefore not cause the required revalidation/rebuild. [Signature implementation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)
- Numerical stability: variance uses `E[x²] - E[x]²`, then clamps negative results to zero. This can conceal catastrophic floating-point cancellation for large-offset, low-variance data. Use a numerically stable state representation or clearly restrict the numerical guarantees. [Variance implementation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)
- MIN/MAX complexity: insertion maintenance can be constant-time, but deleting the current extremum requires recomputing it from the underlying group. The blanket `O(1)` description therefore needs qualification. [README](https://github.com/CAFxX/matview?utm_source=chatgpt.com) [Recomputation implementation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)
- Limitation severity: `LimitationSeverity.WARNING` and `BLOCKER` exist, but `_enforce_limitations()` rejects all limitations unless explicitly ignored. Either implement severity-aware behavior or document the deliberately fail-closed policy. [Implementation](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)

## 3. SQL parsing and feature set

The SQL parser is the largest technical-debt risk.

The current implementation relies on regular expressions and custom string scanning. For example, the comment stripper and top-level SQL splitter understand single- and double-quoted strings, but not the complete range of identifier and literal quoting supported by the target engines. The schema parser also silently skips statements it cannot recognize. [SQL scanning](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com) [Schema parsing](https://github.com/CAFxX/matview/blob/master/matview_sync.py?utm_source=chatgpt.com)

That creates an especially dangerous failure mode: interpreting SQL incorrectly rather than rejecting it.

Recommendation: implement the existing sqlglot TODO early. Use an AST, with dialect-specific parsing and generation, and normalize into the project’s own IR. Keep original SQL fragments for expressions that are intentionally opaque. Make unsupported syntax fail explicitly, with a useful diagnostic.

One important caveat: sqlglot is a parser and transpiler, not a substitute for database-specific semantic validation. Engine-version-specific behavior still needs its own capability checks.

The feature set is already ambitious:

| Feature                    | Assessment / improvement                                                                    |
| -------------------------- | ------------------------------------------------------------------------------------------- |
| Single-table aggregates    | Strong core; improve numerical and edge-case guarantees.                                    |
| Inner/cross joins          | Valuable; expand mutation and join-cardinality stress tests.                                |
| `DISTINCT` aggregates      | Good auxiliary-state approach; document memory and maintenance costs.                       |
| Set operations             | Useful; document duplicate and NULL semantics explicitly.                                   |
| CTEs / derived tables      | Avoid heuristic unwrapping; normalize through the AST.                                      |
| Window functions           | Fallback is sensible; disclose full-refresh costs.                                          |
| LEFT JOIN / recursive CTEs | Keep as fallbacks until efficient incremental rules are proven.                             |
| Index generation           | Add cost-based choices and explain why each index is proposed.                              |
| Multi-engine support       | Good breadth, but distinguish actual engine/version support from compatibility assumptions. |

I would add an `EXPLAIN MATERIALIZED VIEW` equivalent that reports, for each view:

- Selected strategy and rationale.
- Per-operation maintenance complexity.
- Auxiliary tables and indexes.
- Unsupported or potentially dangerous mutations.
- Estimated refresh costs and known limitations.

This is arguably more valuable than adding several more SQL constructs.

## 4. Review of the TODO list

The existing TODOs are sensible, but I would substantially reorder them. [TODO.md](https://github.com/CAFxX/matview/blob/master/TODO.md?utm_source=chatgpt.com)

| Existing TODO                                    | My recommendation                                                                                                                                                  |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Replace regex parsing with sqlglot               | Top priority. Foundation for reliable future work.                                                                                                                 |
| Format / optimize generated SQL                  | Formatting now; optimization after IR and cost model exist.                                                                                                        |
| Avoid duplicate computations across views        | High-value next step; share common delta expressions and auxiliary state.                                                                                          |
| Allow MVs to reference other MVs                 | Introduce a dependency DAG, topological update ordering, cycle detection and transaction-level semantics.                                                          |
| Async, bulk-based and atomic flavours            | Define freshness, visibility, failure recovery and replay guarantees before implementing. These are distinct consistency models, not simply optimization switches. |
| Generate SQL as efficiently as a senior DBA      | Replace this aspiration with measurable cost models, statistics, `EXPLAIN` feedback, engine capabilities and benchmark-driven optimization.                        |
| Engine/version detection                         | Move high in priority; use explicit capability profiles, not just broad dialect labels.                                                                            |
| Consider/propose existing and additional indexes | High value once the planner has a cost model.                                                                                                                      |
| Index auxiliary/materialized tables              | Treat as part of the planner, with workload-dependent recommendations.                                                                                             |
| Support every engine/version                     | Expand incrementally through conformance testing rather than promising universal compatibility.                                                                    |
| Document generated SQL for every feature         | High priority; publish representative before/after SQL and a dialect/strategy support matrix.                                                                      |
| Docker-based integration testing                 | Worth doing; reproducible local integration tests should match CI.                                                                                                 |
| Support NewSQL engines                           | Defer until the core dialect abstraction is stable.                                                                                                                |

In particular, I would not begin with shared computation or materialized-view dependencies. Both add substantial complexity to dependency management and transaction ordering. Get the single-view correctness model solid first.

## 5. Testing, documentation and project usability

There are some genuinely good foundations here.

The differential fuzzer and regression corpus are exactly the right testing approach for a system that generates complex SQL. The CI workflow also has a broad multi-engine matrix, including PostgreSQL major versions and SQLite-compatible implementations. [Fuzzer tests](https://github.com/CAFxX/matview/blob/master/test_matview_sync.py?utm_source=chatgpt.com) [CI workflow](https://github.com/CAFxX/matview/blob/master/.github/workflows/ci.yml?utm_source=chatgpt.com)

However:

- Add deterministic concurrency tests for registration, rebuilding, incremental backfill and `bulk_changes()`.
- Test multiple independent connections, not just the connection used by the manager.
- Add explicit 64-bit bitwise aggregate tests and numerical-stability tests.
- Add performance regression benchmarks, especially for multi-row DML against Tier 2 and Tier 3.
- Run longer randomized fuzzing in scheduled CI and preserve minimized failing cases permanently.
- Test schema changes involving foreign keys, conflict policies and other constraints.

One documentation problem deserves immediate attention: the README reports 3,583 views and 71,480 assertions, while the test-file header reports 6,200 views and 52,633 assertions, and the actual runner invokes 13 suites rather than the 10 stated in that header. [README](https://github.com/CAFxX/matview?utm_source=chatgpt.com) [Test header](https://github.com/CAFxX/matview/blob/master/test_matview_sync.py?utm_source=chatgpt.com) [Test runner](https://github.com/CAFxX/matview/blob/master/test_matview_sync.py?utm_source=chatgpt.com)

Generate these statistics from actual test output rather than maintaining them manually.

I'd also add:

- A dialect/version/feature support matrix, including the chosen maintenance strategy and complexity.
- A section documenting unsupported mutations and consistency guarantees.
- More examples of the generated SQL, not just the CLI workflow.
- An explicit license and packaging metadata if the intention is to make the project reusable as a library. The current visible root contains the main module, test module, README, TODO and CI configuration, but no visible license or packaging manifest. [Repository files](https://github.com/CAFxX/matview?utm_source=chatgpt.com)

## Recommended implementation order

| Priority | Work                                                        | Why                                                    |
| -------- | ----------------------------------------------------------- | ------------------------------------------------------ |
| 1        | Fix backfill races and atomic/recoverable installation      | Fundamental consistency and data-loss risks.           |
| 2        | Fix SQLite `REPLACE` behavior and 64-bit bitwise aggregates | Concrete correctness defects.                          |
| 3        | Fix Tier 3 statement-level refresh behavior                 | Prevent pathological DML costs.                        |
| 4        | Migrate parser to AST + typed IR                            | Eliminate a major source of future bugs.               |
| 5        | Introduce capability profiles and `EXPLAIN` output          | Make behavior understandable and predictable.          |
| 6        | Improve numerical stability, indexing and cost estimation   | Strengthen performance and result guarantees.          |
| 7        | Shared computations and MV dependencies                     | Expand scalability and expressiveness.                 |
| 8        | Asynchronous maintenance and additional engines             | Extend the architecture once its guarantees are solid. |

Bottom line: I like the core idea and the breadth of functionality. The project has the beginnings of a useful database-independent incremental materialization compiler, and its testing philosophy is promising. But I would currently treat it as an ambitious prototype rather than a production-ready transparent materialized-view engine.

The biggest improvement would be to make correctness guarantees explicit and enforceable. In particular, installation, rebuilds, concurrent backfills, SQLite connection behavior, and fallback costs need to be resolved before expanding the feature set.

Review scope: static inspection of the current `master` source, README, TODOs, tests and CI configuration. I did not execute the test suite; the findings above are code-level findings and recommendations, not a claim that I reproduced every failure at runtime.
