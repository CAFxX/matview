## 1. Executive assessment

The project has made substantial progress since reviews 1–3: SQLGlot parsing/builders, Jinja2 templates, SQLAlchemy connectivity and introspection, version-aware code generation, Docker integration infrastructure, a broad native-engine CI matrix, property-based testing, independent-session concurrency tests, a stronger differential oracle, index-intelligence work, and a proposed modular compiler package.

That progress does **not** yet establish production-grade correctness. The release-blocking invariant remains that a materialized reader must be observationally equivalent to the original SQL view after every supported mutation and transaction sequence. Current evidence still contains native PostgreSQL execution failures, MySQL/MariaDB multi-writer backfill failures, transaction-ownership gaps, incomplete lifecycle serialization, and an insufficient drift signature. Several fixes exist only in open PRs and are not validated on their exact current heads.

Most important findings:

1. **P0 — PostgreSQL transition-table maintenance emits invalid SQL** for aggregates grouped by expressions and containing AVG recomputation. Exact-head CI for #197 and #219 fails on PostgreSQL 15/18 with an ungrouped-column error.
2. **P0 — Native MySQL/MariaDB multi-writer backfill tests fail** on MySQL 8.4/9.7 and MariaDB 10.11/11.8/12.3 with BrokenBarrierError. This is not passing concurrency coverage.
3. **P0 — Lifecycle and bulk-operation transaction guarantees remain incomplete on trunk.** MySQL DDL can implicitly commit caller work; trigger-bypass setup/cleanup still has best-effort exception paths; manager initialization, replacement and registration need one explicit transaction-ownership protocol.
4. **P0 — Installed-view signatures are incomplete.** They omit compiler/codegen version, target engine/subdialect/version, relevant FK actions, collation/unique/index metadata and the generated maintenance contract.
5. **P0 — Native aggregate alias semantics remain unresolved on trunk.** #197 attempts a fix, but its CI is red and native differential coverage is still required.
6. **P1 — The proposed frozen LogicalIR is only shallowly immutable.** Frozen dataclasses contain mutable dictionaries and lists; MappingProxyType protects only the outer schema mapping.
7. **P1 — Documentation contains concrete object-name inaccuracies**, and the documented local test commands do not run the complete set of standalone regression suites.
8. **P1 — The native PR stack is not merge-ready.** #214 is 25 commits behind current master and diverged; #215 is not based on the current #214 head; upper layers inherit red CI. The wider queue has 54 open PRs and duplicate/superseded branches.

**Recommendation:** do not treat the current state as release-ready and do not merge the current P0 or modularization stack. Fix P0 correctness and lifecycle issues first, rebase/restack bottom-up, then require green checks on each exact current head. The green master run validates only its own SHA, not the unmerged fixes or current stack.

## 3. P0 — correctness and transaction-safety findings

### P0.1 PostgreSQL expression-GROUP-BY transition-table recomputation emits invalid SQL

**Evidence:** exact-head CI run 44056858297 for #219 and 44057530245 for #197 both fail the full test suite on PostgreSQL 15 and 18. The server log shows an INSERT trigger query grouping transition rows by COALESCE(__mv_new_rows.region, 'UNK') while a correlated AVG subquery refers to raw, ungrouped __mv_new_rows.region. PostgreSQL rejects it with:

> subquery uses ungrouped column "__mv_new_rows.region" from outer query

The failing generated statement is for a view containing AVG(amount) and an expression grouping key. This is a runtime trigger failure: a valid base-table INSERT fails when maintenance runs.

The vectorization helper has a fallback guard for some non-simple grouping expressions and recomputation aggregates, but the observed SQL proves that the guard does not cover every path that emits the transition-table body. Trace planner strategy selection through AVG decomposition, transition-table body generation and dialect emitter selection. Do not assume that returning a null vectorized body at one helper boundary guarantees that the caller uses the row-loop fallback.

**Required work:**
- Reproduce on native PostgreSQL 15 and 18 with a minimal table/view grouped by COALESCE; also test CASE, CAST, arithmetic and other supported expression keys.
- Exercise initial population and INSERT/UPDATE/DELETE, including multi-row transition tables and NULL groups.
- Ensure correlated recomputations reference projected/grouped keys or a joined key relation, not raw ungrouped transition-row expressions.
- If correct set-based SQL cannot be emitted, select the known-correct row-level fallback for the entire affected plan and expose the selected path in diagnostics.
- Add a regression asserting successful DML and equality with the native live SELECT after every mutation.
- Run with transition tables/vectorization enabled and disabled on both PostgreSQL versions. Transpiled SQLite is not validation.

**Priority:** release-blocking. Keep vectorization disabled for this shape until fixed.

### P0.2 Native MySQL/MariaDB concurrent multi-writer backfill is not passing

**Evidence:** #217 and descendant #219 add barrier-synchronized concurrent writer tests. Exact #219 CI fails the native MySQL-family barrier test on MySQL 8.4/9.7 and MariaDB 10.11/11.8/12.3. The exception is BrokenBarrierError in the backfill progress callback at the mid-run barrier. The same SQLite barrier test passes. Earlier stack CI run 43858495281 has the same cross-version failure.

The test waits at a three-party barrier from the backfill progress callback while both writer threads are expected to arrive after a series of DML operations. The timeout establishes that the intended interleaving was not reached; it does not establish whether workers errored, were blocked on locks held by backfill/trigger maintenance, or the barrier protocol itself is incorrectly ordered. Worker-error collection must be inspected before the timeout is converted into a pass or skip.

**Required work:**
- Make worker exceptions and progress state observable before waiting at the second barrier.
- Avoid a blocking callback that can deadlock the operation being tested; use explicit events and a bounded deterministic schedule.
- Distinguish writer attempted DML, statement reached server, transaction committed, and trigger-maintained reader became visible.
- Verify independent sessions complete the supported interleaving without lost, duplicated or double-applied deltas.
- Add rollback/retry, PK-boundary, group-key and offset-batch coverage for MySQL and MariaDB.
- Run repeatedly under CI to expose timing sensitivity.
- If engine locking/isolation makes an interleaving unsupported, fail/serialize explicitly and document the guarantee.

**Priority:** release-blocking for claims of independent-session concurrent backfill on MySQL/MariaDB.

### P0.3 Installation, replacement and manager initialization lack one explicit transaction-ownership protocol

The P0 lifecycle backlog remains real on trunk. Every code path must distinguish a caller-owned transaction from a manager-owned transaction and must never commit, roll back or implicitly commit caller work without an explicit documented contract.

Important subproblems:

- **MySQL/MariaDB DDL implicitly commits.** Catalog alterations, trigger drops/creates, table replacement and other DDL cannot be treated as rollback-safe savepoint work. A caller may lose unrelated uncommitted work if a manager path performs DDL in that transaction.
- **Manager construction can mutate catalog state.** Catalog initialization and migrations must not silently commit caller work. PostgreSQL errors caught after failed DDL can leave the transaction aborted unless rollback/savepoint handling is deliberate.
- **Registration and replacement have multiple externally visible stages.** Creating storage, installing maintenance triggers, populating, publishing the reader, updating catalog metadata and removing old objects must form one explicit lifecycle protocol. On engines where DDL cannot be transactional, reject unsafe in-transaction replacement before the first side effect or implement a documented shadow/cutover protocol.
- **SQLite registration writer isolation is only proposed in #188.** It acquires BEGIN IMMEDIATE before structure/trigger installation and population, which is the right direction, but the PR is based on an old master SHA and has no exact-head checks.
- **Connection wrappers need reliable transaction state.** If an adapter cannot expose whether a transaction is active, the code must not guess and then issue BEGIN or commit on the caller's behalf.

Relevant open work includes #188–#196 and older/superseded counterparts #173, #174, #176, #178 and #187. These are not validated merely because PR descriptions claim a guard or rollback test.

**Required work:** finish the P0 transaction-ownership items in TODO.md, add native failure-injection tests at every lifecycle stage, and verify preservation of unrelated caller work after success and failure on SQLite, PostgreSQL, MySQL and MariaDB.

### P0.4 bulk_changes() remains unsafe when trigger bypass or restoration fails

The trunk implementation attempts session-local trigger bypass on PostgreSQL/MySQL, catches exceptions, and can fall back to dropping triggers. Its cleanup/restoration path contains broad best-effort exception handling. If trigger restoration fails and the exception is suppressed, base tables can continue accepting writes while the materialized reader is no longer maintained. On MySQL, trigger DDL can also implicitly commit caller work.

The manager must either restore the maintenance path and prove it, or fail closed and make the affected connection unusable. It must not report success or return a connection to a pool with a bypass variable still set.

Open work in #102, #115, #118 and #152 is not yet a substitute for a trunk guarantee. #115's stated DML-only MySQL path and connection-discard behavior require exact native MySQL/MariaDB tests; #102's restoration-failure injection must prove restoration failure is surfaced and no subsequent write can silently leave stale results.

**Required work:**
- Remove broad catch-and-ignore paths from correctness-critical trigger suspension/restoration.
- Use a transaction/savepoint only when the engine and connection state support the intended semantics.
- Reject unsafe DDL modes before touching caller work or maintenance objects.
- Poison/invalidate/close a MySQL connection if a session-scoped bypass flag cannot be reset.
- Verify trigger/function inventories and compare live SELECT with the materialized reader after success, exceptions, cancellation and injected cleanup failures.
- Test nested bulk contexts, caller-owned transactions, pool/proxy wrappers and multiple selected views.

### P0.5 Dialect-native statistical aggregate aliases remain wrong on trunk

The parser maps aggregate spellings through a dialect-independent alias table after parsing with SQLite-oriented aggregate semantics. In PostgreSQL, VARIANCE is sample variance and STDDEV/STD are sample standard deviation; MySQL/MariaDB and SQLite use population semantics for these aliases. The same source spelling can require a different canonical aggregate by target engine.

#197 implements target-engine resolution after compilation identifies the dialect, but its exact-head CI fails on PostgreSQL and multiple SQLite-compatible jobs. Its description also explicitly says native PostgreSQL and MySQL/MariaDB differential coverage remains required. The implementation is not complete until those tests exist and pass.

**Required work:** preserve original function spelling through parsing, resolve semantics only after target subdialect selection, and compare values and result types against native live aggregate queries for initial population and INSERT/UPDATE/DELETE. Include singleton/multi-row groups, NULLs and all supported aliases.

### P0.6 Drift signatures do not represent the generated maintenance contract

The current master implementation of _compute_signature (matview_sync.py around lines 13676–13690) hashes comment-stripped raw SELECT SQL, object prefix, generated index DDL, and referenced table columns' names, declared data types, NOT NULL flags and primary-key flags.

It does **not** include compiler/generator version or a stable code-generation fingerprint, target engine/subdialect/version, relevant foreign-key cascade actions, collations, unique/index metadata, or the actual generated backing/reader/trigger contract. It also hashes raw SQL text rather than normalized semantics, so formatting-only changes can trigger rebuilds while generator changes can leave old triggers installed.

This is dangerous because the project supports engine-version-dependent code generation and engine-specific limitations such as MySQL cascading foreign keys. A schema or generator change can alter installed-object behavior without changing the current signature.

**Required work:**
- Define a versioned canonical signature schema.
- Include normalized view semantics, compiler/codegen version, dialect/subdialect/version and every schema property affecting plan selection or generated maintenance.
- Include relevant FK actions, unique constraints/indexes, collation, generated-column/type semantics and capability decisions used by the compiler.
- Prefer hashing the canonical generated plan contract (DDL and maintenance statements) plus explicit semantic inputs.
- Fail closed when required metadata cannot be introspected.
- Add migration tests showing each relevant change is detected and formatting-only changes are not.

### P0.7 SQLite REPLACE and per-connection initialization must remain explicit

SQLite's REPLACE conflict algorithm can perform an implicit delete whose delete triggers do not fire unless recursive triggers are enabled. #195 proposes an explicit initializer for every writer connection. Until this is available and documented, the project must not imply that one manager's connection configuration automatically configures independent application writer connections.

Expose and document a verifiable writer-connection initializer; test it on sqlite3/APSW/SQLCipher/libSQL and prove every connection which can mutate base tables has the required settings. Test REPLACE/INSERT OR REPLACE with PK and unique-key conflicts, delete-trigger retractions, rollback and multiple independent writers. If the library cannot configure an application-owned writer connection, reject or explicitly mark that mutation path unsupported.

### P0.8 Continue closing DML paths that bypass trigger maintenance

Keep limitation checks/tests for MySQL TRUNCATE and FK cascades, but broaden the audit to every supported engine and DML form. Include conflict replacement, cascaded deletes/updates, partition/table swaps, bulk loaders, disabled triggers, session bypass variables, DDL changing base-table shape, and engine-specific conflict/UPSERT syntax. Every unsupported path must be detected or documented as an explicit application responsibility; no silently stale reader is acceptable.

### P0.9 Differential oracle and fuzz campaign still need structural and semantic completion

The current test infrastructure is substantially better than the original fixed battery, but TODO.md correctly keeps open: genuine schema generation, recursive schema-aware DML generation, recursive query AST generation with measured production/combination coverage, independent native oracles, exact type/result metadata, mutation sensitivity beyond comparator-only mutants, metamorphic invariants and broad concurrency coverage.

The main test file remains a very large combined harness. Headline counts such as thousands of generated views or assertions do not establish structural diversity, native execution or sensitivity. Keep generated-case counts separate from schema/query/DML production coverage and native engine coverage.

Finish the explicit P0 oracle/fuzzer tasks in TODO.md. Every generated case must report whether it ran natively, was transpiled, mocked or skipped. Keep unsupported-plan and best-effort override cases separate. Do not suppress limitation warnings in a way that makes unsupported cases look supported.

## 4. P1 — architecture, maintainability, API and documentation

### P1.1 The modular package is a substantial improvement, but its immutable IR guarantee is shallow

#214 splits the monolith into engines, logical_ir, sql_frontend, connectivity, planner, compiler, manager, dialect and maintenance modules. The facade keeps matview_sync.py as a compatibility entry point. This is a good direction and addresses the largest architecture recommendation from reviews 1–3.

However, the new data model is not deeply immutable:

- TableSchema is frozen but stores columns as a mutable Dict.
- IncrementalBackfillSpec is frozen but stores chunk_sql_templates as a mutable List.
- PlanDiagnostics is frozen but contains mutable lists and a mutable details Dict. Its to_dict method makes only shallow copies; nested dict/list values remain shared.
- LogicalIR is frozen but accepts mappings in uall_grp_alias_map and uall_orig_item_map without enforcing immutable copies.
- CompilationContext wraps outer schemas mappings in MappingProxyType, but contained TableSchema objects still expose mutable columns dictionaries.
- Other public plan/diff structures contain mutable lists or mutable dataclasses.

Existing modular-package tests check dataclass field assignment and a few compiler mutation paths, but do not prove deep immutability. A frozen outer object is not sufficient when nested objects can be changed after compilation.

**Required work:**
- Normalize all mutable inputs at construction boundaries.
- Use tuples and recursively immutable mappings (or private copies with read-only public access) for IR/context/plan/diagnostics.
- Ensure nested diagnostic output is detached from internal state.
- Test attempts to mutate every nested collection and verify neither compiler context nor an already-produced plan changes.
- Define which public result types are intentionally mutable and do not describe them as immutable.
- Preserve facade compatibility and validate the complete exported API.

### P1.2 Modularization PR is not merge-ready and needs a real compatibility review

#214 changes 54 files with 26,677 additions and 11,717 deletions. Its complete GitHub diff exceeds the API's 20,000-line diff limit. The new package tests focus on importability, selected facade identity, shallow IR immutability, two compiler mutation cases and CLI help. Those are useful smoke tests, not sufficient evidence that a 15k-line compiler/manager extraction preserved behavior.

Run the full existing deterministic, differential, concurrency, P0 and P1 suites against the package branch on every supported native engine. Add exhaustive facade-export parity, import-order/circular-import, CLI/API parity and serialization/typing compatibility tests. Compare generated plans and executed behavior between the old facade implementation and modular implementation for a representative corpus; the independent live-view oracle remains authoritative. Ensure package modules do not introduce import-time database/dependency side effects.

The manager and SQL frontend remain very large modules (about 2,086 and 2,034 lines respectively), while maintenance/single.py is about 2,000 lines. Split by stable responsibility only where it improves ownership and testability. Verify all public imports documented in README and existing downstream usage remain valid.

### P1.3 README object names are factually inconsistent with the generator

README.md around line 32 says the backing storage table for customer_sales is __matview_customer_sales_data. The current generator's _backing_table_name (matview_sync.py around lines 4336–4338) generates the bounded name using the prefix plus store_ plus the logical view name, i.e. __matview_store_customer_sales under the default prefix. These are not the same object.

The module-level docstring at the top of matview_sync.py is also stale: it says the user-facing read-only view is prefixed as __matview_<view>, while the current compiler uses the declared logical view name. README's user-facing-name explanation is the correct intended contract; the module docstring and backing-table example need to be reconciled with actual generated DDL.

Derive object-name examples from real generated plans in tests or documentation fixtures. Check every README example and public docstring against generated names for default/custom prefixes, including identifier truncation/collision behavior.

### P1.4 Local test commands are not a complete or unambiguous representation of CI

Makefile's test target runs test_matview_sync.py, test_concurrent_backfill.py, test_query_ast_fuzzer.py, test_query_ast_materialization.py and test_docker_test_env.py. It does not run the complete collection of standalone P0/P1 regression programs, test_strength_reporting.py, test_cli_diff.py, test_oracle_adversarial_boundaries.py and other individual tests that CI runs. README describes test_matview_sync.py as the deterministic unit/integration suite and lists some additional scripts, but does not provide one obvious canonical command that runs all required local tests.

The CI matrix uses different Python versions for different jobs: SQLite Python jobs exercise 3.11 and 3.15, while native PostgreSQL/MySQL/MariaDB jobs use their configured Python runtime. Documentation should state the per-job matrix rather than imply every engine is tested under both Python versions.

Create one canonical local command that runs every non-secret test CI expects developers to run (or explicitly label a smaller fast suite and a full suite). Make README, Makefile, Docker runner and CI agree. Document native versus transpiled/emulated coverage and per-job Python versions accurately.

### P1.5 Normalize database type metadata instead of asserting driver-specific formatting

Current #197 CI fails test_08_pull_schema_from_existing_database_across_all_dialects on multiple SQLite-compatible jobs because the assertion compares DECIMAL(18, 4) and DECIMAL(18,4). Precision and scale are the same; the difference is formatting. This is a brittle test failure and may also expose inconsistent normalization at the schema-introspection boundary.

Parse/normalize type declarations into semantic representation (base type, precision, scale, modifiers) and compare that representation. Preserve the original declaration separately when required for round-tripping. Do not weaken assertions so materially different numeric types compare equal.

### P1.7 Packaging and release hygiene remain incomplete

The root has requirements.txt but no pyproject.toml, setup.py, package metadata, declared supported Python range, version source, license file or release/build workflow. A package directory in #214 does not by itself make the project installable as a supported distribution.

Keep test helpers independent from production internals. Do not split mechanically without clear module ownership.

## 5. P2 — feature and performance roadmap

P2 work remains subordinate to P0 correctness and P1 maintainability.

### P2.1 Partition-scoped Tier 2 window maintenance is not accepted yet

#219 adds partition-scoped window maintenance and native tests. Its exact-head CI is red because of inherited PostgreSQL transition-table SQL failures and MySQL/MariaDB concurrency barrier failures. Do not mark the feature complete or enable it broadly until its own native tests pass after inherited failures are fixed.

The semantic contract must cover: recompute only affected partitions; same-partition ORDER BY changes; primary-key ORDER BY changes; partition-key-only changes; NULL partition keys; multiple partition expressions and ties; native live-SELECT comparison after INSERT/UPDATE/DELETE; and planner fallback when a safe partition predicate cannot be proved.

### P2.2 Index intelligence needs correctness and cost evidence

#218 adds base-index introspection, recommendations and automatic auxiliary/backing indexes. Recommendations must derive from actual generated access paths, be deduplicated and dialect-correct, and not create duplicate/incorrect indexes across rebuild, shadow swap, drift repair and drop. Existing user indexes and constraints must be preserved. Current PR CI is not green on its exact stack head because the stack has inherited failures.

Before completion, measure representative write overhead and maintenance latency as well as read/trigger improvements. Recommendations should remain advisory unless the user opts into index creation.

### P2.3 Continue the remaining SQL feature roadmap only after the correctness gate

The existing TODO priorities remain appropriate for LEFT OUTER JOIN algebraic maintenance, reference-counted MIN/MAX and bitwise aggregates, cascading materialized views, multi-view trigger consolidation/shared sub-aggregation, asynchronous/bulk refresh, NewSQL/CDC paths, ORM/migration integrations and the SQL construct showcase. Do not expand supported syntax until each feature has a native semantic oracle, a clear unsupported boundary and a measured maintenance cost.

## 7. Historical review delta

Reviews 1–3 correctly identified original architecture and testing weaknesses. Significant recommendations have since been implemented or are represented by active work: SQLGlot parsing/builders, Jinja2 templates, SQLAlchemy connectivity, version parsing, Docker Compose integration, native engine CI, property-based tests, independent-session concurrency tests, stronger result comparison, index intelligence and a modular package proposal.

Some earlier statements are now stale and must not be repeated as current facts. In particular, the user-facing materialized view is now intended to retain its logical SQL name; it is not generally exposed as a prefixed __matview_<view> reader. The README backing-table example is also inaccurate, as noted above. The modular package is still a PR, not trunk.

Remaining high-value themes from earlier reviews are still relevant: atomic lifecycle semantics, transaction ownership, a truly independent oracle, multi-view dependencies/shared work, asynchronous refresh, measurable access-path quality and an honest per-engine feature contract.
