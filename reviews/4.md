## Policy and process risks

1. **Native stack membership is unverified.** The base/head chain is not sufficient proof of GitHub native stack membership. The available GitHub actions inspected here expose ordinary PR/base/ref operations and auto-merge, but no native stack create/link/rebase/inspect operation. Do not claim that the stack is linked or rely on automatic stack advancement without verifying it through GitHub's stack UI/API.
2. **Merge-method terminology needs reconciliation.** Repository metadata reports merge commits disabled, squash disabled and rebase merge enabled. GitHub rebase-and-merge preserves a linear history, but it is not a literal fast-forward of the PR branch ref. Keep the desired history invariant explicit and verify that the configured merge mechanism actually satisfies it; do not silently equate the two.
3. **Exact-head validation is essential.** The old PR #188/#197 base and every stack descendant must be compared against the latest trunk/predecessor SHA. Green results on a prior head do not authorize merge after a rebase or push.
4. **Avoid blind retries.** Re-running the same failing workflows without a code/test change is unlikely to help. Diagnose the native PostgreSQL SQL and MySQL/MariaDB barrier behavior first.
5. **Do not bulk-enable auto-merge until native stack membership, per-layer diffs, and the required checks are verified.** Auto-merge is enabled at repository level, but the queue is not yet in a state where enabling it indiscriminately is safe.
