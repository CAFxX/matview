# `matview` Roadmap & Prioritized TODO List

This document tracks all feature goals, architectural improvements, and verified findings from the project roadmap and independent code reviews.

  A deterministic differential-testing harness and permanent regression corpus exist (`DifferentialSQLFuzzer` in Suite 12 + Suite 13). This is only infrastructure, not completion of comprehensive schema/query/DML fuzzing: the current scenario structure and DML operations are template-driven, schema topology is largely fixed, and the oracle/engine simulation/concurrency coverage still need the work listed under P0.
- [x] **Live Database Schema Introspection Tests**:
  I would like the tests to exercise also pulling the schema from an existing database (`introspect_database_schemas` tested across SQLite, PostgreSQL, and MySQL/MariaDB in `test_08_pull_schema_from_existing_database_across_all_dialects`).
- [x] **Unified Multi-Dialect Testing Infrastructure**:
  I would like all tests to be unified (taking care of using the right dialects) on top of the same shared testing infrastructure so that even when you're just running the sqlite tests in memory you exercise all the shared infrastructure used also when testing with other engines e.g. mysql/pg (`TranspiledConnectionAdapter` + `MVTestRunner`).
- [x] **Autodetect or Accept Target Engine & Version (`--engine-version` / `detect_engine_version`)**:
  I would like the generator to autodetect (when connecting to the database) or accept as arg the engine and version, so that it can autoselect the correct and most efficient dialect/subdialect (`EngineSubdialect`, `EngineVersion`, `parse_engine_version`, `detect_engine_version`, and `--engine-version` across SQLite, PostgreSQL, MySQL, and MariaDB, including PostgreSQL 15+ `UNIQUE ... NULLS NOT DISTINCT` group indexes, PostgreSQL 10+ transition-table gating, MariaDB vs MySQL subdialect detection, and SQLite 3.24+ UPSERT / 3.25+ window-function version checks).
- [x] **AST/Token-Backed SQL Parsing, Formatting & Strict Dialect Identifier Quoting (`sqlglot`)**:
  Avoid brittle regex-only SQL parsing by delegating SQL tokenization, AST parsing, formatting, and dialect-specific identifier quoting (`"ident"` on SQLite/PostgreSQL, `` `ident` `` on MySQL/MariaDB) to `sqlglot` (`requirements.txt`, `parse_sql_ast`, `parse_view_ast`, `tokenize_sql`, `quote_sql_identifier`, `format_sql`) so base tables, columns, or aliases containing reserved keywords (`"order"`, `"group"`, `"select"`, `"where"`), spaces (`"unit price"`), or punctuation never break generated DDL or trigger SQL.
- [x] **Snapshot-Isolated & Watermark-Gated Chunked Incremental Backfills (`incremental_backfill=True`; mechanism implemented, correctness/recovery still P0)**:
  The snapshot and watermark mechanisms exist, but their complete correctness is not established: initialization ordering, NULL watermark state, failed non-snapshot batches, incomplete-registration visibility, resume/retry, and watermark persistence still have explicit P0 work below. Do not interpret this infrastructure as a completed concurrency guarantee. Original design:
  - Support snapshot-isolated backfills (`REPEATABLE READ` on PostgreSQL, `START TRANSACTION WITH CONSISTENT SNAPSHOT` on MySQL, `SAVEPOINT` on SQLite via `snapshot_isolation=True`), and
  - Track the active backfill cursor watermark (`backfill_cursor_pk`, `backfill_max_pk`, `backfill_active`) in `__matview_catalog` so concurrent row triggers gate on the watermark and never double-count or under-count rows in the pending range.
- [x] **Native Composite Keys & Group-Column Indexes for Nullable Group Columns, Joins & `UNION ALL` Views**:
  Eliminate string-serialized `__mv_pk` surrogate keys (`quote(a) || '|' || quote(b)`, `ROW(...)::TEXT`, `CONCAT_WS('|', ...)`) where supported:
  - Use native composite `PRIMARY KEY (col1, col2, ...)` whenever `GROUP BY` columns are `NOT NULL` across single-table, `INNER JOIN` / `CROSS JOIN`, and `UNION ALL` aggregate views, and native `PRIMARY KEY (__mv_branch_id, __mv_pk_0, ...)` on `UNION ALL` Z-set views,
  - Use `UNIQUE NULLS NOT DISTINCT (col1, col2, ...)` on PostgreSQL 15+ for nullable group keys across single-table, Join, and `UNION ALL` views, and
  - Index both composite group keys and individual non-leading `GROUP BY` columns so engines can perform index scans on any grouping column.
- [x] **Welford Running-Variance (`mean`, `M2`) & Chan Parallel Merge for IEEE-754 Float Engines**:
  Complement PostgreSQL `NUMERIC` and MySQL `DECIMAL(65, 12)` variance accumulators with Welford's centered sum-of-squares (`__mv_m2_*`) single-row update/downdate rules, Chan's parallel batch-merge formula, and anchor-shifted initial `M2` calculation for SQLite `REAL` columns, eliminating IEEE-754 catastrophic cancellation on high-offset values (e.g. `1e9 + delta` and `1e12 + delta`).
- [x] **Session-Scoped & Shadow-Table Swap `bulk_changes()` Isolation (mechanisms implemented; fail-closed and transaction guarantees remain P0)**:

In particular, do not claim global-trigger-drop is impossible until the P0 acceptance tests below pass. Original design: Avoid dropping maintenance triggers globally across concurrent connections during `bulk_changes()` by supporting session-local trigger bypass flags (`SET LOCAL matview.skip_triggers = 'on'` in PostgreSQL, `@__matview_skip_triggers = 1` in MySQL), transactional `SAVEPOINT` isolation in SQLite, and atomic shadow-table rebuild + `ALTER TABLE ... RENAME` swap (`use_shadow_swap=True`).
- [x] **Atomic Single-Transaction Registration & Single-Shot Initial Backfill (not incremental/replacement lifecycle; remaining gaps are P0)**:
  The single-shot path has an atomic transaction mechanism. This does not establish atomic replacement, atomic DDL on MySQL, incremental-backfill atomicity/recovery, or reader invisibility during incremental population; those remain explicit P0 requirements below.
- [ ] **Serialize Initial Registration & Backfill Across Engine-Specific DDL Boundaries**:
  Registration must not expose an unpopulated reader view or allow a concurrent base-table write to be omitted or counted twice while backing/auxiliary structures and maintenance triggers are installed and the initial population runs.
  - Progress: PostgreSQL can use transactional DDL for single-shot registration. SQLite requires an explicit write reservation before DDL because its Python driver does not automatically transact DDL; PR #90 adds `BEGIN IMMEDIATE` and an independent-connection regression (exact-head CI pending).
  - MySQL/MariaDB implicitly commit around DDL, so the previous claim that the entire registration sequence is one atomic transaction is not valid for those engines. An engine-specific protocol is still required to serialize/reconcile concurrent writers across trigger installation and initial population, and to prevent readers from observing a partially initialized reader view.
  - Add native MySQL/MariaDB independent-session tests synchronized at trigger installation, population start, and reader-view publication. Verify no lost/double-counted writes, no partially initialized reader visibility, and correct recovery after failures at each DDL/transaction boundary.
- [x] **Safe Batch-Size Substitution in `MaterializedViewPlan.get_populate_statements`**:

- [x] **Exception-Safe `bulk_changes()` Context Manager**:
  Roll back uncommitted base-table mutations and cleanly restore maintenance triggers without committing dirty state when an exception is raised inside a `with manager.bulk_changes():` block.
- [x] **Strict Compilation Mode (`strict=True` / `--strict`)**:
  Raise `StrictCompilationError` when `strict=True` (or `--strict` on the CLI) is set and a view cannot be compiled with Tier 1 `ALGEBRAIC_DELTA` maintenance, preventing silent fallback to expensive Tier 2/Tier 3 refreshes on large production tables.
- [x] **Native Composite Primary Keys for Single-Table Projections & MySQL `NOT NULL` Group Keys**:
  Preserve the base table's actual primary/composite key columns in `_compile_tier1_zset_projection` and enable native composite `PRIMARY KEY (col1, col2, ...)` on MySQL `NOT NULL` `GROUP BY` views instead of synthesizing concatenated `__mv_pk` strings.
- [x] **`SELECT *` and `SELECT DISTINCT *` Tier 1 Expansion**:
  Expand `SELECT *` and `SELECT alias.*` on single-table views against `primary_schema.columns` so `SELECT * FROM t [WHERE ...]` and `SELECT DISTINCT * FROM t [WHERE ...]` compile with Tier 1 $O(1)$ `ALGEBRAIC_DELTA` maintenance instead of falling back to Tier 3.

## P0 — Test Correctness & Coverage Gaps

- [ ] **Make Original-View Equivalence the Universal, Release-Blocking Correctness Gate**:
  The non-negotiable contract is that, for every supported view, engine/version, and valid base-table mutation sequence, the materialized reader result is observationally equivalent to executing the original view against the current base tables. Any discrepancy is a bug. The differential oracle must execute the original SQL natively against the same database state and remain independent of compiler, trigger, backing-table, and refresh implementation details. Compare row multisets (including duplicate multiplicity), values, NULLs, grouping keys, and result types; exact types remain exact, with only narrow documented tolerances for legitimate approximate floating-point evaluation-order differences. Check initial population and all relevant mutation/transaction paths, including INSERT/UPDATE/DELETE/UPSERT, bulk operations, rollback, backfill, and concurrent sessions. Systematically cross supported query structures, DML shapes, types, NULLs, constraints, and engine/version combinations. Minimize every mismatch into a permanent deterministic regression. Demonstrate test sensitivity with representative injected faults/mutation testing. Never relax the oracle, skip a failing case, or widen tolerances merely to make tests pass; prove any accepted difference is allowed by the SQL/engine contract. Reject unsupported behavior explicitly rather than returning a divergent result. This is a release-blocking invariant, not an aspirational test-count target.

The existing differential-testing harness is useful, but its current headline counts must not be treated as evidence of broad structural coverage. In particular, the schema/scenario generator is largely fixed-structure, DML is selected from a finite set of hardcoded operation templates, query generation recombines predefined patterns, some dialect paths are transpiled to SQLite, numerical comparisons normalize values too aggressively, and the backfill interleaving test does not use independent concurrent sessions. Keep the existing deterministic tests and regression corpus, but do not consider the fuzzing goal complete until the following are implemented and measured.

- [ ] **Preserve MySQL/MariaDB Caller Transactions in `bulk_changes()` When DDL Paths Are Requested**:
  MySQL-family DDL (including `CREATE/DROP TRIGGER`, `CREATE/DROP TABLE`, and `RENAME TABLE`) implicitly commits the active transaction. The current `bulk_changes()` implementation can execute these statements when `use_shadow_swap=True`, when trigger bypass is unavailable, or when `drop_triggers=True`; a surrounding application transaction can therefore be committed even if the context later fails. Before `get_catalog()` or any other manager query can itself start a DB-API transaction, detect whether the caller already owns a transaction. Reject transaction-unsafe DDL modes before changing state, or provide a genuinely DML-only alternative. Do not claim rollback/atomicity for a MySQL DDL path. Add native MySQL and MariaDB regressions proving (1) a caller transaction remains uncommitted and rollback-able on the supported DML-only path, (2) unsafe DDL options fail before any caller work is committed or triggers are changed, and (3) exception cleanup does not silently commit caller work. Also cover adapters without a reliable transaction-state API explicitly rather than guessing.
  
- [ ] **Preserve Dialect-Native Statistical Aggregate Alias Semantics**:
  The aggregate parser currently canonicalizes `VARIANCE` to `VAR_POP` and `STDDEV` / `STD` to `STDDEV_POP` in a dialect-independent map, while parsing aggregate expressions with the SQLite SQLGlot dialect. This loses native semantics on engines where the aliases differ: PostgreSQL defines `VARIANCE` as sample variance and `STDDEV` as sample standard deviation, whereas MySQL defines them as population statistics. Preserve the original function spelling and resolve aliases using the target engine/subdialect (or reject unsupported/ambiguous aliases explicitly); do not infer semantics from the SQLite parser dialect. Add native PostgreSQL and MySQL/MariaDB differential tests for initial population and INSERT/UPDATE/DELETE maintenance, including singleton and multi-row groups, and verify both values and result types against the engine's live aggregate query.
